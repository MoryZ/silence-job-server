# 项目流程说明文档

本文档用于说明 Silence Job Server 的整体业务流程与运行机制，重点回答三个问题：任务如何创建、任务如何调度、任务如何执行与兜底。

配套的 Mermaid 时序图见 [JOB_FLOW_SEQUENCE_DIAGRAMS.md](JOB_FLOW_SEQUENCE_DIAGRAMS.md)。

## 1. 项目定位

Silence Job Server 是一个分布式任务调度平台，核心能力包括：

1. 支持 Job 任务创建与配置。
2. 支持按时间触发、固定间隔触发等调度方式。
3. 支持集群、分片、广播、MapReduce 等执行模式。
4. 支持失败重试、死信处理和告警通知。
5. 支持工作流编排，把多个任务串成一条业务链路。

## 2. 核心角色

### 2.1 Job

Job 是任务定义本身，保存任务的基础属性和调度规则，例如：

1. 任务名称和所属组。
2. 触发方式 `triggerType`。
3. 执行器类型 `executorType` 和执行器信息 `executorInfo`。
4. 参数内容 `argsStr` 和参数类型 `argsType`。
5. 阻塞策略、重试次数、重试间隔、超时时间等控制参数。

### 2.2 JobTask

JobTask 是一次具体执行实例。Job 定义的是“要做什么”，JobTask 定义的是“这一次实际做了什么、结果如何”。

### 2.3 JobTaskBatch

JobTaskBatch 是一次调度批次，用来把同一轮触发产生的任务实例聚合起来，便于状态追踪和批量处理。

### 2.4 Retry / RetryTask

Retry 表示失败后需要进入重试链路的业务记录，RetryTask 表示具体重试执行实例。

### 2.5 NotifyConfig / NotifyRecipient

NotifyConfig 定义告警规则，NotifyRecipient 定义通知接收人，两者通过关联表进行绑定。

### 2.6 Workflow / WorkflowNode

Workflow 用于编排多个 Job，WorkflowNode 表示工作流中的节点。

## 3. 整体流程

项目的主流程可以概括为下面这条链路：

1. 用户创建 Job。
2. 服务层把 Job 保存到数据库。
3. 调度器周期性扫描待触发任务。
4. 到点后生成 JobTaskBatch 和 JobTask。
5. 时间轮触发执行器执行任务。
6. 执行成功则回写结果，执行失败则进入重试和告警链路。
7. 超过最大重试次数后进入死信队列。

## 4. 任务创建流程

任务创建通常来自管理端接口。用户提交任务名称、执行器、触发方式、参数、重试策略等信息后，系统会完成以下动作：

1. 校验基础字段。
2. 计算 `nextTriggerAt`。
3. 设置 `bucketIndex`，用于后续分桶扫描。
4. 写入 `sj_job`。

创建阶段的关键是把“业务配置”转成“可调度配置”。其中 `nextTriggerAt` 是调度判断的核心字段。

## 5. 调度流程

调度层会定时扫描 `sj_job`，找出满足触发条件的任务：

1. 任务状态是开启。
2. 当前时间已经达到或接近 `nextTriggerAt`。
3. 任务所在分桶满足本轮扫描范围。

扫描到任务后，系统不会直接执行，而是先生成批次和任务实例，再注册到时间轮。这种方式把“发现任务”和“执行任务”解耦，便于扩展和容错。

## 6. 执行流程

执行层会根据任务类型选择不同执行器：

1. `ClusterJobExecutor`：集群执行。
2. `ShardingJobExecutor`：分片执行。
3. `MapReduceJobExecutor`：MapReduce 处理。
4. `BroadcastJobExecutor`：广播执行。

执行器通过 RPC 调用远程节点完成真正的业务逻辑。执行完成后，系统会把结果回写到 `JobTask` 和 `JobTaskBatch`。

## 7. 失败重试流程

如果任务执行失败，系统不会立刻判定任务结束，而是进入重试链路：

1. 先发布失败事件。
2. 生成 Retry 记录和 RetryTask。
3. 按 `retryInterval` 重新调度。
4. 继续尝试，直到成功或达到 `maxRetryTimes`。
5. 如果仍失败，就进入死信队列 `sj_retry_dead_letter`。

这个设计保证了失败任务有明确的处理路径，而不是简单丢弃。

## 8. 告警通知流程

任务失败、超时或进入死信后，会触发告警流程：

1. 发布告警事件。
2. 监听器异步接收告警。
3. 查询通知配置和接收人。
4. 组装告警内容。
5. 通过邮件、钉钉、企业微信等渠道发送。

通知配置和接收人之间采用关联表管理，这样多个 Job 或 Workflow 可以复用同一套告警配置。

## 9. 数据表与职责对应

| 数据表 | 作用 |
|---|---|
| `sj_job` | 任务定义 |
| `sj_job_task` | 任务执行实例 |
| `sj_job_task_batch` | 调度批次 |
| `sj_retry_task` | 重试执行实例 |
| `sj_retry_dead_letter` | 死信数据 |
| `sj_notify_config` | 通知配置 |
| `sj_notify_recipient` | 通知接收人 |
| `sj_workflow` | 工作流定义 |
| `sj_workflow_node` | 工作流节点 |

## 10. 这套设计的特点

1. 配置驱动：Job 的属性决定整个任务生命周期。
2. 解耦清晰：创建、调度、执行、重试、告警各自分层。
3. 可追踪：批次、任务、重试、死信都有独立记录。
4. 可扩展：执行器类型和工作流节点都可以继续扩展。
5. 可运维：失败告警和死信链路便于问题定位。

## 11. 一句话总结

这个项目本质上是一个“配置驱动的分布式任务调度与重试平台”：先创建 Job，再由调度器扫描触发，执行器完成实际任务，失败后进入重试和告警链路，最终形成闭环处理。
